# 001. 混合架构：稀疏精确执行替代稠密近似

- 状态：accepted（2026-09-13）
- 背景（全部为实测，非推测）：
  - 图 16444 dims / 1915 lookups（2026-09-14 基线），MILP 128 层；99 个注意力层里 **65 层零 lookup**，每层 head 需求直方图最大 395、多数 ≤7（`docs/HYBRID_ARCH.md`），全局 `H=400` 是 31× 浪费。
  - 路由 softmax 的分数实测 **1e9–1e10**（`HARD_K=1e4` 温度逼 one-hot）：fp16 上限 65504 → inf → NaN；bf16 尾数 8 位 → 语料 0/12 正确；fp32 精确（最大槽值 1.6e6 < 4.2e6 安全界）。
  - 稠密权重 post-WP8 约 **24 亿参数 / 19GB**，本机 22GB 可用内存下必然 OOM；非零密度实测 **5.6e-05**（508M → 6–7 万 nnz）。
  - 消融实验证明注意力**是**载荷性的（置零后全部用例超时）——之前"注意力无用"的结论是 hook 假象，见 `开发防线.md` §1.1。
- 决策：保留 Transformer 的**残差流 + Persist 稠密语义**作为承载状态的主干；把三处纯浪费换成精确执行：
  1. 死注意力层在 `runner` 与 `weights` 两条热路径上按 `out_weight` 非零判定折叠（2.3–3.9× 提速，逐 token 一致）；
  2. 逐层 head 容量 `H_li`，L4SV 升 **v2**（头部后加每层 head 数组，引擎仍读 v1）；
  3. 路由改**精确 argmax + gather**（对缩放不敏感，与浮点精度解耦），算术走 **CSR 稀疏**，编译直接吐 `.sbin` 不 materialize dense。
- 被拒方案：
  - 继续稠密 fp32/fp16 近似：19GB 放不下，且 fp16/bf16 判定不稳定，等于把验收交给数值运气。
  - 用训练补偿编码误差：违反 `docs/DESIGN.md` §6 非目标（不训练），且验收要求判定确定而非"通常对"。
  - 保留全局 `H=400`：31× 的循环浪费直接决定"证明规模下是否可用"，不可接受。
  - 完全去掉注意力机制改成查表程序：那就不再是 Transformer，放弃了"一份权重自回归执行内核"这一目标本身。
- 预期后果：
  - 好：artifact 19GB → 11.3MB、编译数十秒、路由不再受精度绑死、逐层异构容量成为可扩展点。
  - 坏：Python 稠密 runner 与 C++ 稀疏引擎变成两条实现，语义必须持续对齐（`tests/test_engine_vs_runner.py` 目前因缺产物没在跑，见任务 004）；hardmax 成为默认后，softmax 分支变成纯调试用途（`VM_SOFTMAX=1`）；`.sbin` 格式变更需版本化纪律。
